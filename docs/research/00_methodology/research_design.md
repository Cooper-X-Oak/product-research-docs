# 调研设计

## 1. 调研目标

本轮调研要回答一个产品机会问题：

是否应该把第一阶段 MVP 定位为“人工审核的外贸 B2B 线索研究交付包”，而不是泛化为 AI CMO、中国版 Okara、内容工具或通用 Agent 平台。

## 2. 研究方式

本项目采用逐点调研，不采用先写总报告再补证据的方式。

```text
业务问题
|
+-- 独立问题页
|   +-- agent-reach / 全网搜索
|   +-- 来源表
|   +-- 命令记录
|   +-- 失败渠道记录
|   +-- 事实发现
|   +-- 分析解释
|   `-- MVP 影响
|
`-- 综合报告
    +-- 只引用前置问题页
    `-- 不替代逐点证据
```

## 3. 信源组合

每个重点问题优先覆盖至少 3 类信源：

| 信源类型 | 用途 | 例子 |
|---|---|---|
| 官网 / 官方文档 | 确认产品自我定位、功能边界、价格口径 | Okara、Salesforce、Apollo、Hunter |
| 第三方研究 / 媒体 | 校验行业趋势和非产品方叙事 | McKinsey、Deloitte、媒体报道、评测 |
| 社媒 / 社区 | 获取真实使用者、从业者和早期市场反馈 | Reddit、X、V2EX |
| 视频平台 | 获取中文市场语境、服务商和实践案例 | B站、YouTube |
| 小红书 / 内容平台 | 获取本地商家、代运营、内容运营侧信号 | 小红书 |
| 价格 / 服务包页面 | 判断客户已经为什么付费 | SaaS pricing、海关数据、代运营套餐 |
| GitHub / 开源项目 | 判断技术可行性、工作流成熟度 | browser automation、agent workflow |

## 4. 事实、推断、建议的分层

每个问题页必须区分：

| 层级 | 说明 |
|---|---|
| 事实 | 来源中直接可验证的信息，例如产品功能、价格、公开表述、社区反馈 |
| 推断 | 基于多条事实的解释，例如“当前类别更像工作流包装而不是完整 CMO 替代” |
| 建议 | 对 MVP 方向、定价、交付或验证计划的行动建议 |

## 5. 置信度规则

| 置信度 | 判断标准 |
|---|---|
| 高 | 多类信源互相印证，且关键事实来自一手来源或高可信第三方 |
| 中 | 有足够来源，但部分来源偏营销叙事、样本有限或缺少价格/真实用户数据 |
| 低 | 来源不足、渠道失败较多、或关键结论依赖推断 |

## 6. 当前已知限制

- LinkedIn MCP 当前未配置；LinkedIn 相关信息需要用公开网页、Jina Reader 或其他公开来源兜底。
- X/Twitter OpenCLI 在首次调研中出现未登录错误；如果后续仍失败，只作为失败渠道记录，不伪造社媒证据。
- Jina Reader 在首次 curl 测试中没有返回内容；后续需要继续重试，并记录失败或替代读取方式。
- Exa 在 doctor 中显示可用，但 `mcporter call exa.web_search_exa` 当前提示未知 MCP server；后续需要记录该矛盾并用普通网页搜索兜底。
